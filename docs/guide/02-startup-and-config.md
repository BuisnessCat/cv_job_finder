## install.ps1 — установка

Скрипт PowerShell, запускается один раз (повторный запуск безопасен). Делает три вещи:
создаёт виртуальное окружение, ставит зависимости, кладёт ярлык на рабочий стол.

| Строки | Что происходит | Зачем |
|---|---|---|
| [2](../../install.ps1#L2) | `$ErrorActionPreference = "Stop"` | Любая ошибка команды PowerShell останавливает скрипт, а не идёт дальше. |
| [3-4](../../install.ps1#L3-L4) | `$root = $PSScriptRoot`, путь к `.venv\Scripts\python.exe` | `$PSScriptRoot` — папка, где лежит сам скрипт. Скрипт работает одинаково, откуда бы его ни запустили. |
| [6-9](../../install.ps1#L6-L9) | если `.venv` нет — `py -3.11 -m venv .venv` | `py` — лаунчер Python для Windows, `-3.11` выбирает версию. Если окружение уже есть, оно не пересоздаётся. |
| [8](../../install.ps1#L8), [11](../../install.ps1#L11) | проверка `$LASTEXITCODE` | `ErrorActionPreference` не действует на внешние программы (`py`, `pip`), их код возврата приходится проверять вручную. |
| [10](../../install.ps1#L10) | `pip install -r requirements.txt` | Ставит зависимости в `.venv`, а не в системный Python. |
| [13-20](../../install.ps1#L13-L20) | ярлык через COM-объект `WScript.Shell` | Стандартный способ создать `.lnk` из PowerShell. |

Поля ярлыка:

- `TargetPath` — `.venv\Scripts\pythonw.exe`. **`pythonw`** вместо `python`: у `python.exe` всегда
  открывается чёрное окно консоли, у `pythonw.exe` — нет. Обратная сторона: `print()` и тексты
  ошибок некуда выводить, поэтому всё пишется в `job_finder.log`.
- `Arguments` — `-m job_finder`: запустить пакет как программу. Python находит папку
  `job_finder/` и выполняет её `__main__.py`.
- `WorkingDirectory` — корень проекта. Это важно для `-m`: Python ищет пакет `job_finder`
  в текущей папке.
- `IconLocation` — `job_finder\icon.ico,0` (`,0` — номер иконки внутри файла).

## \_\_main\_\_.py — точка входа

### `acquire_lock(path)` — [строка 16](../../job_finder/__main__.py#L16)

```python
lock = QLockFile(str(path))
return lock if lock.tryLock(0) else None
```

`QLockFile` — файл-блокировка Qt. `tryLock(0)` пытается занять файл `job_finder.lock`
и **не ждёт** (0 мс): если файл занят другим запущенным экземпляром, сразу возвращает `False`.

Тонкости:

- В файл записывается PID процесса. Если процесс умер, не удалив файл (а у нас он не удаляется —
  см. `os._exit` ниже), следующий `tryLock` видит, что процесса с таким PID нет, и считает
  блокировку «протухшей» (stale) — забирает её. Поэтому оставшийся после закрытия
  `job_finder.lock` не мешает следующему запуску.
- Блокировка держится, **пока жив объект** `QLockFile`. Поэтому `main()` хранит его в переменной
  `lock` до самого выхода: если бы объект удалился сборщиком мусора, блокировка снялась бы.

### `main()` — [строка 22](../../job_finder/__main__.py#L22), по шагам

1. **Лог** ([23-26](../../job_finder/__main__.py#L23-L26)). `logging.basicConfig` настраивает корневой
   логгер: писать в `job_finder.log` в UTF-8, уровень INFO и выше, формат
   `время уровень имя_модуля: сообщение`. Все модули создают свой логгер
   `logging.getLogger(__name__)`, поэтому в логе видно, откуда сообщение (`job_finder.worker`,
   `job_finder.llm`, …).

2. **Исключения в лог** ([28](../../job_finder/__main__.py#L28)). `sys.excepthook` — функция, которую
   Python вызывает для необработанного исключения. По умолчанию она печатает трассировку в консоль,
   которой у `pythonw` нет. Мы заменяем её на `logging.critical(..., exc_info=...)` — трассировка
   попадает в лог. Исключения фонового потока сюда не попадают (для потоков есть отдельный
   `threading.excepthook`), но `Worker._run()` и так ловит всё сам и пишет в лог.

3. **Свой AppUserModelID** ([30](../../job_finder/__main__.py#L30)). Windows группирует окна на
   панели задач по этому идентификатору. Без него наше окно считалось бы окном `pythonw.exe` и
   показывалось бы с иконкой Python. `ctypes.windll.shell32` — прямой вызов функции Windows API.

4. **`QApplication`** ([31](../../job_finder/__main__.py#L31)). Главный объект любого Qt-приложения
   с окнами. Должен быть создан **до** любых виджетов, и он один на процесс.

5. **Иконка** ([32](../../job_finder/__main__.py#L32)) — для всех окон приложения: заголовок и
   панель задач.

6. **Тема приложения** ([33](../../job_finder/__main__.py#L33)) — `style.apply_app_theme(app)`
   ([style.py:94](../../job_finder/style.py#L94)). Она делает две вещи, которые не задаются стилями окна:
   - `setColorScheme(Dark)` просит Qt и Windows рисовать тёмными заголовок окна и системные диалоги
     (например, «Приложение уже открыто»). Метод появился в Qt 6.8.
   - задаёт зелёный цвет ссылок в палитре приложения: ссылки из Markdown в окне «Резюме» Qt красит
     именно цветом палитры приложения, правила стилей и палитра самого виджета на них не действуют.

7. **Блокировка второго запуска** ([35-38](../../job_finder/__main__.py#L35-L38)). Зачем: два окна
   работали бы с одной моделью `job-finder` в LM Studio, и закрытие одного окна выгрузило бы модель
   посреди оценки у другого. Если блокировка занята — сообщение и `os._exit(0)`.

8. **`db.init()`** ([39](../../job_finder/__main__.py#L39)) — создать таблицу, если её нет.

9. **Окно и цикл событий** ([40-42](../../job_finder/__main__.py#L40-L42)). `app.exec()` запускает
   цикл событий: обработка кликов, перерисовка, таймеры, сигналы из фонового потока. Функция
   возвращает управление, только когда закрыто последнее окно.

10. **`os._exit(code)`** ([44](../../job_finder/__main__.py#L44)). Мгновенный выход из процесса
    без обычной «уборки» Python. Обычный выход стал бы аккуратно завершать интерпретатор, пока
    фоновый поток, возможно, ещё ждёт ответа модели (до 120 с) или обращается к объектам Qt,
    которые уже удаляются. `os._exit` просто завершает процесс. Записи лога при этом не теряются:
    обработчик файла сбрасывает каждую запись в файл сразу после записи.

> **Справка: зачем `if __name__ == "__main__"`** ([47](../../job_finder/__main__.py#L47)).
> При запуске `python -m job_finder` модуль выполняется с именем `__main__` и вызывает `main()`.
> Когда тест делает `from job_finder.__main__ import acquire_lock`, имя модуля другое,
> и окно не открывается.

## config.py — все настройки

Модули обращаются к настройкам как `config.DB_PATH`, а не `from config import DB_PATH`.
Это важно для тестов: `monkeypatch.setattr(config, "DB_PATH", ...)` подменяет атрибут модуля, и
все, кто читает `config.DB_PATH` в момент вызова, видят подменённое значение.

### Пути

| Настройка | Значение | Где используется |
|---|---|---|
| `ROOT` | `Path(__file__).resolve().parent.parent` — корень проекта | основа для остальных путей, блокировка в `__main__` |
| `CV_PATH` | `ROOT / "master_cv.md"` | `worker.read_cv()` |
| `DB_PATH` | `ROOT / "jobs.db"` | `db._connect()` |
| `LOG_PATH` | `ROOT / "job_finder.log"` | `__main__` |
| `ICON_PATH` | `ROOT / "job_finder" / "icon.ico"` | `__main__` |

`__file__` — путь к самому `config.py`; `.parent` — папка `job_finder`; ещё `.parent` — корень.
Так пути не зависят от того, из какой папки запущено приложение.

### Порог

| Настройка | Значение | Смысл |
|---|---|---|
| `MIN_SCORE` | `5` | В таблице только вакансии с оценкой ≥ 5. Используется в `window.load_rows`, `window.on_evaluated`, `worker._refresh` (итог «X подходящих»). Это только фильтр показа: при изменении ничего не переоценивается. |
| `STALE_DAYS` | `14` | Отклик со статусом «Ждём ответа» дольше этого числа дней подсвечивается янтарным: число в колонке «Ждём, дн.», плашка и подсказка в карточке (`window.render_applied`, `window.show_details`). |
