## Справка: что такое LM Studio и как мы с ней работаем

**LM Studio** — программа для запуска языковых моделей на своём компьютере (на видеокарте).
С ней можно работать двумя способами, и мы используем оба:

1. **Консольная утилита `lms.exe`** — управление: запустить сервер, загрузить и выгрузить модель,
   посмотреть, что загружено. Мы вызываем её через `subprocess`, как будто набираем команды
   в терминале.
2. **HTTP-сервер на `localhost:1234`** — сама работа с моделью. Он повторяет API OpenAI:
   `POST /v1/chat/completions` принимает список сообщений и возвращает ответ модели. Поэтому
   запрос выглядит так же, как к ChatGPT API, только адрес локальный.

```
llm.prepare()  ── lms server start ──► сервер LM Studio (localhost:1234)
               ── lms ps --json ─────► какие модели загружены?
               ── lms load … ────────► модель в видеопамяти под именем job-finder
llm.evaluate() ── POST /v1/chat/completions ──► ответ модели (JSON)
llm.release()  ── lms unload job-finder ──────► видеопамять свободна
```

**Модель** — `mistralai/ministral-3-8b`: 8 миллиардов параметров, около 6,5 ГБ, целиком помещается
в 12 ГБ видеопамяти RTX 3060 и отвечает сразу, без режима «размышлений». Модель
`qwen/qwen3.8-27b`, которая тоже скачана, в 12 ГБ не помещается и перед ответом долго «думает».

## JSON-схема ответа `SCHEMA` — [строка 15](../../job_finder/llm.py#L15)

Модель обязана ответить JSON-объектом ровно такой формы:

| Поле | Тип | Смысл | Где видно в окне |
|---|---|---|---|
| `score` | целое 1–10 | насколько реально пройти отбор | колонка «Оценка», плашка в карточке |
| `summary` | строка | 1–2 предложения: почему такая оценка | блок «Почему такая оценка» |
| `have` | список строк | важные требования, которые у кандидата есть | «ЕСТЬ» (зелёные ✓) |
| `missing` | список строк | существенные требования, которых нет | «НЕ ХВАТАЕТ» (красные ✕) |
| `risks` | список строк | настоящие блокеры | «МОЖЕТ ОТСЕЧЬ» (жёлтые !) |

`"required": [...]` — все пять полей обязательны; `"additionalProperties": False` — других полей
быть не может.

> **Справка: structured output.** Схема передаётся в запросе в `response_format` с `"strict": True`.
> LM Studio тогда ограничивает генерацию: на каждом шаге модели разрешены только те токены,
> которые не нарушают схему. В результате ответ — всегда синтаксически правильный JSON нужной формы,
> и не нужно «вытаскивать» JSON из свободного текста.

## Правила оценки `RULES` — [строка 28](../../job_finder/llm.py#L28)

Это системный промпт — инструкция модели. Устроен так:

1. **Роль** ([28-29](../../job_finder/llm.py#L28-L29)): «помогаешь студенту решить, стоит ли
   откликаться», шкала 1–10.
2. **Как оценивать** ([31-45](../../job_finder/llm.py#L31-L45)), четыре пункта:
   - выделить суть роли и 2–4 *действительно* обязательных требования; длинные списки технологий —
     пожелания, за второстепенные инструменты не снижать;
   - засчитывать близкие навыки (Django/Flask ≈ FastAPI, MySQL/MSSQL ≈ PostgreSQL);
   - на junior-позициях недостающие технологии — повод учиться, а не отказ;
   - сильно снижать только за **настоящие блокеры** (2+ года опыта, другой основной язык или область,
     свободный чешский или английский C1+, офис вне Праги без удалёнки, гражданство другой страны) —
     и отдельно перечислено, что блокером **не** является.
3. **Шкала** ([47-52](../../job_finder/llm.py#L47-L52)): что значит 9–10, 7–8, 5–6, 3–4, 1–2.
4. **Формат ответа** ([54-61](../../job_finder/llm.py#L54-L61)): что класть в каждое поле, не больше
   5 пунктов по 10 слов, по-русски, без Markdown, только по фактам.
5. Последняя строка — `Резюме кандидата:`, и сразу за ней в запросе приклеивается текст резюме.

**Почему правила такие подробные.** Модель на 8B параметров сначала оценивала слишком буквально:
считала обязательной каждую технологию из вакансии и почти всё получало низкие оценки. Правила
переписали так, чтобы отделять обязательное от пожеланий и снижать только за настоящие блокеры:
подходящих стало 23 из 259 вместо 9.

## `fingerprint()` — [строка 67](../../job_finder/llm.py#L67)

```python
return f"{config.MODEL}\n{RULES}"
```

«Отпечаток» всего, что влияет на оценку, кроме резюме. `worker.read_cv()` смешивает его с текстом
резюме и берёт SHA-256 — получается ключ оценки. Изменили модель или хоть одну букву в `RULES` —
ключ другой — все вакансии переоцениваются (~37 минут).

Что **не входит** в отпечаток и поэтому переоценку **не** вызывает: `SCHEMA`, `temperature`,
`max_tokens`, `MAX_DESCRIPTION_CHARS`, `CONTEXT_LENGTH` и формат текста вакансии в `evaluate()`.

## `ModelLost` — [строка 72](../../job_finder/llm.py#L72)

Исключение для особой ситуации, найденной на практике. Окно LM Studio (оно работает в фоне,
после того как `lms` его запустил) может переключить свой чат на другую модель; при настройке
«выгружать предыдущую модель при выборе» наша `job-finder` выгружается. Дальше LM Studio
**молча** отвечает на запросы к `job-finder` той моделью, которая загружена, — и мы бы сохранили
чужие оценки.

Защита — в `evaluate()`: в ответе есть поле `model`, и если там не `job-finder`, выбрасывается
`ModelLost`. `worker` на это исключение останавливает весь проход (оценивать дальше нечем).

## `_lms(*args, timeout=120)` — [строка 76](../../job_finder/llm.py#L76)

Обёртка над `subprocess.run` для вызова `lms.exe`:

| Аргумент | Зачем |
|---|---|
| `[str(config.LMS_EXE), *args]` | команда и её аргументы списком (без строки для оболочки — безопасно, не нужно экранировать) |
| `stdin=subprocess.DEVNULL` | если `lms` вдруг что-то спросит, он сразу получит «конец ввода», а не будет ждать вечно |
| `capture_output=True` | перехватить вывод, чтобы прочитать его в `result.stdout` / `result.stderr` |
| `text=True, encoding="utf-8", errors="replace"` | получить строки, а не байты; непонятные байты заменить, а не упасть |
| `timeout=120` | не ждать больше 2 минут (иначе `TimeoutExpired`) |
| `creationflags=CREATE_NO_WINDOW` | Windows не показывает мелькающее окно консоли |

Возвращает `CompletedProcess` (`returncode`, `stdout`, `stderr`). Исключение при ненулевом коде
возврата **не** выбрасывается (`check=True` не указан) — код проверяет вызывающий.

## `prepare()` — [строка 92](../../job_finder/llm.py#L92)

По шагам:

1. **Есть ли `lms.exe`** ([94-95](../../job_finder/llm.py#L94-L95)). Нет — `RuntimeError("не найден …")`.

2. **Запущен ли сервер** ([96-108](../../job_finder/llm.py#L96-L108)). Если нет —
   `lms server start --port 1234`, затем раз в секунду проверяем `_server_up()`, максимум 30 с.
   `time.monotonic()` — часы, которые не прыгают при переводе системного времени, для замеров
   интервалов это правильный выбор.

   **Почему здесь вывод не перехватывается** (`stdout=DEVNULL`, а не `capture_output`). Команда
   `lms server start` запускает фоновую службу LM Studio, и та наследует открытые каналы вывода
   своего родителя. Если бы мы перехватывали вывод, `subprocess.run` ждал бы, пока каналы закроются,
   а служба держит их открытыми, пока живёт, — то есть вечно. `timeout` тут не спасает: на Windows
   после истечения таймаута `subprocess.run` убивает процесс `lms` и **ещё раз** дочитывает каналы,
   снова повисая. С `DEVNULL` каналов нет, и ждать нечего. Этот случай закреплён тестом
   [test_prepare_starts_server_without_capturing_output](../../tests/test_llm.py#L57).

3. **Загружена ли модель** ([109](../../job_finder/llm.py#L109)). `lms ps --json` печатает список
   загруженных моделей в JSON; проверяем, есть ли в выводе подстрока `job-finder`.

4. **Загрузка модели** ([111-117](../../job_finder/llm.py#L111-L117)), таймаут 5 минут:

   ```
   lms load mistralai/ministral-3-8b --identifier job-finder --context-length 8192 --gpu max --ttl 300 -y
   ```

   | Флаг | Значит |
   |---|---|
   | `--identifier job-finder` | имя, под которым модель будет видна в API |
   | `--context-length 8192` | размер контекста в токенах |
   | `--gpu max` | все слои модели — на видеокарту (иначе часть считалась бы на процессоре, медленно) |
   | `--ttl 300` | если к модели 300 с никто не обращался, LM Studio выгрузит её сама. Страховка на случай, если приложение закроется посреди загрузки и `unload` не дойдёт |
   | `-y` | не задавать вопросов, подтверждать автоматически |

   Ненулевой код возврата → `RuntimeError("модель не загрузилась: …")` с последними 300 символами
   вывода (там обычно причина).

Любое исключение из `prepare()` ловит `worker` и пишет в строку состояния «LM Studio: …».

## `evaluate(cv_text, job)` — [строка 120](../../job_finder/llm.py#L120)

### Что отправляется

```python
vacancy = (f"Название: {job.title}\nКомпания: {job.company}\nГород: {job.city}\nИсточник: {job.source}\n\n"
           f"{job.description[:config.MAX_DESCRIPTION_CHARS]}")
```

Описание обрезается до 8000 символов, чтобы весь запрос поместился в контекст 8192 токена.

Тело запроса `POST http://localhost:1234/v1/chat/completions`:

```json
{
  "model": "job-finder",
  "messages": [
    {"role": "system", "content": "<RULES>\n<весь текст master_cv.md>"},
    {"role": "user",   "content": "Название: Junior Python Developer\nКомпания: ACME\nГород: Praha\nИсточник: Jobicy\n\n<описание>"}
  ],
  "temperature": 0,
  "max_tokens": 700,
  "response_format": {"type": "json_schema",
                      "json_schema": {"name": "evaluation", "strict": true, "schema": {…SCHEMA…}}}
}
```

| Поле | Зачем |
|---|---|
| `system` = правила + резюме | Одинаковое для всех вакансий. LM Studio запоминает уже обработанное начало запроса и при следующей вакансии пересчитывает только сообщение `user`. Поэтому резюме стоит в системном сообщении, а не рядом с вакансией. |
| `user` = вакансия | Меняется от запроса к запросу. |
| `temperature: 0` | Без случайности: та же вакансия даёт тот же ответ. |
| `max_tokens: 700` | Предел длины ответа, с запасом для пяти полей. |
| `response_format` | Ответ строго по `SCHEMA` (см. справку выше). |
| `timeout=120` | Не больше 2 минут на вакансию. |

### Что приходит и как разбирается

Ответ в формате OpenAI (сокращённо, пример выдуманный):

```json
{
  "model": "job-finder",
  "choices": [{
    "message": {
      "role": "assistant",
      "content": "{\"score\": 7, \"summary\": \"Основа совпадает: Python и SQL…\", \"have\": [\"Python\", \"SQL\"], \"missing\": [\"Django\"], \"risks\": []}"
    }
  }]
}
```

Обратите внимание: `content` — это **строка**, внутри которой JSON. Поэтому разбор в два шага:

```python
response.raise_for_status()                    # 4xx/5xx → исключение
data = response.json()                         # внешний JSON ответа сервера
if data.get("model") != config.MODEL_ID:       # ответила не наша модель
    raise ModelLost(...)
result = json.loads(data["choices"][0]["message"]["content"])   # внутренний JSON — оценка
result["score"] = int(result["score"])         # на всякий случай привести к int ("7" → 7)
return result
```

Что может пойти не так и что будет:

| Ошибка | Исключение | Что делает `worker` |
|---|---|---|
| сервер не ответил за 120 с | `requests.Timeout` | считает вакансию неоценённой, идёт дальше |
| сервер вернул 4xx/5xx | `requests.HTTPError` | то же |
| ответ не JSON или нет нужных ключей | `JSONDecodeError`, `KeyError` | то же |
| ответила другая модель | `ModelLost` | **останавливает весь проход** |

Неоценённая вакансия ничего не теряет: оценки у неё нет, и при следующем обновлении она снова
окажется в очереди.

## `release(wait=True)` — [строка 153](../../job_finder/llm.py#L153)

Выгружает модель: `lms unload job-finder`. Сервер LM Studio остаётся работать — без загруженной
модели он видеопамять не занимает.

- `wait=True` (по умолчанию, вызывается из `worker` в конце обновления) — через `_lms`, ждём
  завершения.
- `wait=False` (из `closeEvent` окна) — через `subprocess.Popen`: процесс запускается, и мы сразу
  идём дальше, не дожидаясь. Окно должно закрываться мгновенно.

Ошибки (`OSError` — например, нет `lms.exe`; `SubprocessError` — например, таймаут) только
пишутся в лог: выгрузка — это уборка, из-за неё нельзя ронять обновление. Это важно, потому что
`worker` вызывает `release()` в `finally`, даже если `prepare()` упал из-за отсутствия `lms.exe`.

## Как перейти на Claude API

Об этом говорит докстринг модуля ([строки 1-2](../../job_finder/llm.py#L1-L2)): остальной код
вызывает только три функции, поэтому достаточно переписать их:

- `prepare()` и `release()` — пустые (облачной модели не нужно загружаться в видеопамять);
- `evaluate()` — запрос к API Anthropic с теми же `RULES`, резюме и вакансией, ответ — словарь с теми
  же пятью полями;
- `fingerprint()` будет содержать новое имя модели — и всё переоценится автоматически.
